# Changelog

## Unreleased

### Added

- **One rulebook for test code.** `skills/achilles-orchestrator/references/test-baseline.md` holds every rule a spec, support module, bundle or k6 script follows, each with an id (`TB-A1` to `TB-G2`), its source, whether it is decidable from the code or needs a reader, its severity (blocking, advisory or advisory until measured), detection, examples and exceptions. It also defines the waiver comment and its caps, the per-test `// defect: <ref>` pointer, the two accepted `test.fail` sentinel forms, "upgrade the framework first" for version gaps, and the framework-gap register with six seed rows. Only the touched test has to be clean.
- **`achilles-spec-lint`, the lint for the rulebook's mechanical rules (framework-surface and governance families).** It reads every `playwright*.config.*` statically to find the spec roots and globs (plus Playwright's default glob and `tests/**`), classifies spec, support, k6 and bundle files, follows imports to find support modules, and tracks driver bindings (fixture parameters, `fx.page`, custom fixtures by type or by what they pass to `use`, hook assignments, destructured members, a repository element's `.locator`, and the driver behind `repo.driver` or `steps.page`). Rules: `TB-A1` to `TB-A5`, `TB-A7`, `TB-A9` to `TB-A14`, `TB-G0` and `TB-G1`, with the severities of the rulebook (`TB-A13` advisory until a change's touched tests are known). Driver methods called by another route (`.call`, `.apply`, `.bind`, a method read off the binding) count as raw calls; bindings held in arrays, objects, iteration variables and a fixtures rest element, aliased test bindings and the fixtures module's namespace are tracked. Waivers excuse one finding each, with the caps per test, hook and helper and per register row across the suite; a waiver that excuses nothing, a gap token whose row does not cover the call and a TB-A1 waiver outside the escape-hatch form are findings; the framework-gap register at `tests/e2e/docs/framework-gaps.md` is validated against the no-equivalent table, which now also lists listeners, context settings and page lifecycle calls. The Steps surface comes from the worktree's `node_modules`, else the main checkout's, else a snapshot shipped per published framework release; `npm run build:equivalents` rebuilds those snapshots and the raw-method equivalence table from the published releases, and `check:pack` checks the shipped tables offline. Output: three lines per finding, or `--json` per `schemas/spec-lint-report.schema.json`; exit 0, 1 (blocking findings), 2 (usage, or no surface resolved) or 3 (time budget). It advises only.
- **`achilles-spec-lint` covers every family of the rulebook.** Flow control (`TB-F1` branches that act or assert, including an IIFE, a one-pass loop, an awaited ternary or `&&` around them, in tests, hooks and shared in-spec helpers; `TB-F3` `.catch(() => <constant>)`, `.then(…, onRejected)` and `Promise.allSettled` in a test body; `TB-F5` fixed waits, with `waitForTimeout` and `pause` unwaivable in specs and sleep helpers resolved across modules; `TB-F6` `.only` (unwaivable) and `test.fail` outside the two sentinel forms; `TB-F2`, `TB-F4` and `TB-F7` advisory), structure (`TB-S1` tests declared in loops, iteration callbacks or a factory called more than once; `TB-S2` a UI-driving spec helper used by fewer than two tests of its file or exported, and classes in specs; `TB-S2a`, `TB-S3`, `TB-S4`, `TB-S7` serial mode without `serial-deliberate:`, `TB-S8` a change under `tests/e2e/inspect/`, unwaivable; `TB-S5`, `TB-S6` and `TB-S9` advisory), identity (`TB-I1` ids in titles, blocking once the project pins its pattern through `CIVITAS_TEST_ID_PATTERN`, `specs.shape.titleIdPattern` or a recorded baseline `idPattern`, else advisory with one project finding; `TB-I2`, `TB-I3` against the scenario blocks, `TB-I4` per-test `// defect:` pointers with paths, anchors and defect ids resolved), and the hints and checks of the R, D, W, X, N, P and K families (`TB-D2` unwaivable; the platform rules stay inert on web projects; k6 scripts get only the k6 rules). The declarative constant-table form of `TB-S1` stays behind one factory-rule setting, `specs.constant-table-tests`, which is off; the rulebook says it is not accepted at present. A test whose title is not a literal is still a test; generated tests are found through describes in loops and factories passed by reference; in hooks only a branch that asserts or drives the UI is `TB-F1`; a class whose framework calls are only `api*`, `request*` or `sql*` is not `TB-S3`. An API client class built from `request` (`constructor(private request: APIRequestContext)` calling `this.request.get(…)`) is not `TB-S3` either; constructing a class from `steps`, the repository or a UI driver binding (not `request`) inside a hook branch counts as driving the UI even when the class only makes API calls. A config-named `globalSetup` or `globalTeardown` module is linted as support wherever it sits, and one project finding counts the code files under the spec roots that are neither spec nor support.
- **Only the touched test is charged.** `achilles-spec-lint --staged` (the index against `HEAD`) and `--base <ref>` (the working tree against the merge-base) mark every finding `touched` or legacy per test, describe and file scope; only touched blocking findings fail the run, a version gap (`TB-A13`) blocks in a touched test, and staged content is what gets linted. `--stdin` reads `{"file","before","after"}` and reports only the findings new in `after`; inside a test a finding is matched by rule, test and message, so an edit of the test's opening line does not re-report what the test already had. `--suite` checks ids across files and lints the support modules a spec imports, with `followedFrom` on their findings. `--id-index` writes `tests/e2e/docs/test-ids.md` and `--id-index --check` compares it with the ids in use.
- **Test-baseline notes while agents write, on both harnesses.** A Write or Edit of a spec or support file by an Achilles agent runs `achilles-spec-lint --stdin` on the before and after text and notes only the findings the write added, blocking ones worded "blocking under the test baseline" with their rulebook anchor; a lint that cannot run, crashes or passes its budget (5 s per file) is a one-line note and the write lands. Each write, and each shell write the Bash judge sees (`sed -i`, redirection, `tee`, `cp`/`mv`, `git checkout <ref> -- <path>`, `git restore`, a `node -e` fs write), is recorded with the git object id it left and its path in the file's own git work tree, so worktree writes are recorded correctly: in the run's `touched` list on Claude Code, in `.achilles/runs/<run-id>/touched.jsonl` on pi. Rows keep the kind the lint gave the file, so scope is decided when they are read, and are capped per agent. When an author hands back, the tests it touched are linted against the commit its dispatch started from, so its own commits count, and the orchestrator gets the blocking findings (a note on Claude Code, a `Compliance:` paragraph on pi). Rewrites the judge cannot read (`perl -pi`, `prettier --write`, `git apply`, …) are not recorded. Nothing is refused on the test baseline. On pi the expert runner now also returns the expert's process id, and a host command run by the guards is killed outright at its timeout and no longer dies on a closed stdin; a command that exits first is reported with its own exit code, also when it left a large stdin unread or a background child holds its output, a command killed by a signal reads as 128 plus the signal (never as the lint's exit 1), and a timed-out lint is noted once ("it timed out after 8000 ms"). The commit an author's hand-back is linted against is read before the author starts, so a commit it makes at once is still counted.
- **Compliance baseline, ratchet and pre-commit check for existing suites.** `achilles-spec-lint --init-baseline` records `tests/compliance-baseline.json` (schema `schemas/compliance-baseline.schema.json`) from `HEAD` only: the blocking findings per file, rule and bucket (test, describe scope, file scope) of the rules ruleset `tb-1` counts, the waived ones, and the test-id pattern the titles already use, which makes `TB-I1` blocking: one id shape that at least 90% of the titles share (a single uppercase prefix, several uppercase segments, or a lowercase convention of any number of segments), widened for ordinary growth (2 to 5 prefix letters and 2 to 4 digits at least, `^\s*([A-Z]{2,5}-[0-9]{2,4})` when every id fits it), else `house-default`. The init prints the pattern and how to pin another before committing. It is refused when the file exists or existed in any ancestor commit, installs the pre-commit check, and says to commit both alone as `chore(test): compliance baseline`. `--pre-commit` (the hook's entry point) lints the commit's real content, also under the temporary index of `git commit -a`, against the baseline at `HEAD`; `--ratchet --base <ref>` does the same for the working tree against the baseline at the merge-base, never the change's own copy; `--ci` adds the deleted test ids and waiver changes. Each fails (exit 1) on a blocking finding in a touched test, on untouched code gaining findings per file, rule, bucket or in the totals (counts are recomputed from the code), and on a copy of the baseline that is deleted, raised above the reference, lowered below the code or has a changed id pattern; renames carry their entry. `--update-baseline` writes only decreases; `--ruleset-upgrade` records the rules a newer ruleset added or promoted, which an older baseline does not compare until then. The checks read the protected rule inputs (the factory rules' `specs.*` and `secrets.*` rules, a committed `.env` id pattern, the framework-gap register, the configs' test selection) from the reference commit, never from the change: `--ci` and `--ratchet` fail a change that weakens one (`[ci] protected input changed`), `--pre-commit` names it. A rule a newer ruleset promotes is held to its count in the reference commit's own code until `--ruleset-upgrade` records it, which may record no more and must be a change of its own; every ruleset after the first lists what it promotes. CI fails a baseline re-created where an ancestor held one and asks a shallow clone for full history (exit 2), and compares through the last valid copy when the reference copy is corrupt. The hook runs the project's installed lint, or a workspace root's above it (it never downloads one), blocks only on exit 1 and warns and lets the commit through when the lint cannot run. It goes in `.githooks/` with a local `core.hooksPath` on a fresh repository, and is chained into an existing setup (called first, right after the shebang line, in husky's `.husky/pre-commit` or the `pre-commit` of a hooks directory inside the work tree, so the hook keeps its own result; a wrapper around a hook that is not a shell script; a command in a lefthook configuration; the local hooks directory when it already runs any hook), never overwriting one and never writing outside the repository: a global, system or outside hooks path is refused with the line to add by hand, and dormant hooks under `.githooks/` stay off unless named with `--activate-hooks`. `--install-hook` installs it in another clone, and running it twice changes nothing. Results are cached in `.achilles/compliance/index.json` by the git object ids of the content (not under `--ci`), so a second check of the same content is answered from it. The time a commit pays is the engine's time plus Node's start-up: on about 200 specs the lint takes about 0.6 s and the whole check about 0.9 s inside the process (0.3 s from the cache), and every real commit is a cold run; the wall-clock time adds the host's process start, about 2 s on a loaded machine. Nothing is refused by Achilles itself; a project opts in by recording the baseline.
- **Doc-drift checks for the rulebook.** `lint-doc-drift.mjs` checks that every rule is reachable at `#tb-<id>`, that rule ids are unique, that every cited `test-baseline.md#…` anchor and every `TB-<id>` named under `skills/`, `docs/` or in this changelog exists, that no other file under `skills/` restates a rule's first sentence, and that every rule whose kind is mechanical has an `achilles-spec-lint` rule and a fixture directory (repository-name resolution and the commit-gate rule input check are the named exceptions).

### Changed

- **Composing skills cite the rulebook.** The canon index, Stage 3, the Stage 4b checklist, spec shape, test identity, the composer's Step 3, the judge's oracle and compliance dimensions and the sentinel phase point at `TB-<id>` rules instead of restating them. Settled on the way: titles use the ` · ` separator; no describe needs its own timeout; a test whose data may be in either state uses a fixture or a named skip instead of branching; conditional Steps members count as flow control in a spec; verbs live in flow modules, or in fixtures held to the verb rules; the oracle must be present and tied to the action, with guards allowed after it; the escape hatch wraps a repository selector in `WebElement` and cites a register row; the verify-change mutation hooks are a sanctioned wiring shape. The verifier's readability check now lists the `TB-<id>` rules it checks, and the Steps API reference marks its conditional members as flow control. Stage 4a's fixture templates (fresh user, reset, API sign-in through the session-aware `steps.requestPost`, cart seeding, banner dismissal, the serial sentinel) now follow the rulebook: fixtures hand out functions, verbs take `steps`, titles carry ids, no literal credentials. The failure-diagnosis step that shared the "Stage 4b" name is now "Selector re-learning", and the bug-discovery reproduction examples carry test ids.

- **One severity scale, as ordered questions.** The severity rubric asks, in order, whether someone loses money, data or access (`critical`), is stopped or misled at the core (`high`), gets a result wrong in part (`medium`) or right with something off (`low`), and covers data that leaves the product as well as what shows on screen. A reproducer's `severity.level` must be one of the five values; ranges, conditions and private scales are refused by the schema.
- **A premise and depth gate (verify-change 4b).** After the diff review the run decides whether the behaviour the criteria describe is still what the environment is meant to do. A premise that a later change superseded or reverted, confirmed by one live look, stops the run with one question instead of a full verification. Runs that go on state `light` or `full` with the reason; light keeps the negative control, defect confirmation and the score and drops the breadth.
- **Drive once, replay everywhere (6f).** The live walk returns a runnable flow script per criterion and a suspect script per suspicion. Reproducers judge and replay the suspect script instead of finding the state again, and record a video only for a `bug`; the author turns the flow scripts into tests instead of walking the flow again.
- **verify-change loops are bounded.** Fourteen measured ticket runs spent a third of their cost on fix, re-review and re-probe dispatches. Step 8b now ends at zero `[must-fix]` findings and at two fix cycles, re-probes only the missions that raised a must-fix, and re-runs only the mutants a fix touched (`achilles-mutate --only a,b,c`). Probe findings carry a `[must-fix]` or `[should-fix]` bracket against a closed list (review skill, Mode 4; `must-fix` in `probe.schema.json`).
- **Reuse first (verify-change 5b).** Existing tests that answer a criterion are run instead of re-explored or rewritten; a re-test, a browser pass and a regression check run existing tests only.
- **Stages merged where the context has room.** Measured peaks: probes about 100 k and reviewers at the end about 90 k, with a third of their cost spent on setup reading; authors about 207 k. So coverage and outcome share a reviewer, assertions and value share one, `probe-rigour` writes the verify note, one doc-writer dispatch writes the phase 9 set, and `probe-verdict` reviews the defect audit. Author and inspector stages are not merged.
- **7a triage.** An observation no criterion or stated promise covers goes to the product owner as a question instead of to a reproducer; two low-severity suspicions on one screen may share a reproducer; an incomplete verdict is completed by the same reproducer.
- **Bug or spec question is decided by the written text.** A product that does otherwise than a criterion or spec row states is a `bug`, also when the code diverges on purpose; `spec-ambiguity` needs two readings quoted from the text.
- **The coverage probe reads what the walk saw.** A recorded observation that contradicts a criterion and has no defect id or test, and a named edge case with no test, are must-fix.
- **One slice per author brief, one pass per document.** An author brief covers one criterion group with all of its edge cases and iterates on those only; documents that cite evidence are written once, after it is final, and reviewed once.
- **Re-verification rounds are scoped to the fix diff.** `verify-change` defines a round and its fix diff, and each step after the first run only looks at what the fix changed. Behaviour that passed before is re-verified by its test going green, not by driving the app again. Step 7 asks for every case checked by hand in step 6 to end up as an assertion in its criterion's test, and the adversarial review mutates only the fix diff's hunks, carrying the other verdicts forward marked as carried.
- **`achilles-mutate` accepts a `specs` list per mutation**, so a mutation runs only the specs that own its criterion. Without it the top-level list runs as before.

### Fixed

- **Briefs and reports named by absolute path.** An orchestrator in a worktree or a nested checkout dispatches with absolute paths, which the adapter did not recognise: it read no brief, and it never found the reproducer's `defect-repro` block in its report, so verdicts went unrecorded and reproducers were dispatched twice. Both forms are read now, and an unrecorded verdict is completed by the same reproducer.
- **A reproducer brief without a defect id or the `defect-repro` schema is named at dispatch.** Such a brief produced a verdict the adapter could not record, and the reproducers were dispatched a second time.
- **Resuming a run from a worktree session.** `delegate_qa` with `run` looked for `resume.json` only in the main work tree, while a session started in a worktree keeps its run state there; it now accepts either.

### Added

- **`ACHILLES_MODEL_ORCHESTRATOR`, `ACHILLES_MODEL_EXPERTS`**: operator model pins for the registered agents. **`ACHILLES_MUTATE_CONCURRENCY`**: the project's default mutation width.

### Fixed

- **Hook type check on Claude Code 2.1.323.** `plugin validate --strict` now type-checks hooks modules, and the untyped `.mjs` imports in `bash-judge.ts` and `dispatch.ts` failed with TS7016 on node 24. `claude-code/data/` gets declaration files for `protected-paths.mjs` and `schema-role-map.mjs`.
- **Skill descriptions over 1,024 characters.** `contract-testing`, `database-testing` and `test-data-conventions` had frontmatter descriptions longer than the 1,024 characters pi accepts, so pi warned at every launch in a project with Achilles installed. They are now 975–1,014 characters, with every trigger and the reason to load each skill kept, and `scripts/lint/registry.mjs` fails a description over 1,024.

### Added

- **Claude Code plugin adapter** under `claude-code/`: the package root is the plugin root (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`), one hook module (`claude-code/hooks.ts`, declared in `claude-code/hooks.json`), shared libraries (shell parser, commit and spend classifiers, import-boundary, test-id and selector-diff scanners), data vocabularies and a spec suite. Install from the marketplace (`claude plugin marketplace add civitas-cerebrum/achilles`, `claude plugin install achilles@achilles`), from a checkout (`claude --plugin-dir .`) or through npm.
- **`delegate_qa`** tool and **`/achilles <task>`** command. Both start the `achilles-orchestrator` agent in the background and answer `RUNNING` plus a run id at once; progress shows in the status line and the Achilles pane; the hand-back is queued as a prompt of its own when the orchestrator's turn completes, so the main session reports it without the user typing.
- **Expert mode on pi** (`pi/index.ts`, declared in `package.json` under `pi.extensions`). `delegate_qa` and `/achilles <task>` run the orchestrator in its own `pi` process; the orchestrator gets an `Agent` tool shaped like Claude Code's and dispatches each expert into a process of its own. Every process is set up from the same `agents/achilles-<role>.md` (prompt, tools mapped to pi's, preloaded skills), so the skills read the same on both harnesses and a new `achilles-<role>` file is a new expert on both. The main session gets no `Agent` tool and experts dispatch nobody. The orchestrator's and experts' processes run the Claude Code adapter's Bash judge and secrets screen as pi guards (`pi/guards.ts`), and `npm install` registers the package with pi when `pi` is on PATH (`ACHILLES_SKIP_PI_REGISTRATION=1` skips it). A `bash` call an Achilles agent makes with no timeout gets 600 s on pi (`ACHILLES_PI_BASH_TIMEOUT`), where pi has no default: one hung command stalled a whole onboarding for four hours. Each orchestrator and expert process keeps its transcript under `.achilles/runs/<run-id>/sessions/` (it ran `--no-session` before, which left a 69-minute idle stall undiagnosable). A `write` or `edit` that would leave a run-state JSON file unparseable is blocked on pi (the onboarding's coverage state lost a `]` mid-run). An orchestrator or expert process exits when its parent is gone (a parent killed by a signal runs no `session_shutdown`). The judge's helpers moved to `claude-code/hooks/io.ts` and its Claude Code registration to `bash-hook.ts`, so it loads outside Claude Code.
- **Defect confirmation (verify-change step 7a) and the `achilles-reproducer` expert.** Every suspected defect, and every defect the run calls "known" without a tracker issue or audit entry, goes to a fresh `achilles-reproducer` (new agent, new skill `defect-confirmation`). It gets the claim with its evidence, the criteria, the live app and the source, but not the suite, the knowledge base or earlier reports, and returns one verdict, `bug` / `real-in-source` / `spec-ambiguity` / `not-a-bug`, as the standard defect evidence: a `defect-repro` JSON block (`schemas/subagent-returns/defect-repro.schema.json`) with the ticket and defect id (`<TICKET>-D<n>`), a reproduction count, the root cause by `file:line`, a severity with its reason, steps a reader with no context can follow, and the evidence captured. The adapter records it as `.achilles/defect-confirmations/<ticket>/<defect-id>.json` (a `bug` needs a live observation). Hook 3 now refuses a bug, rework or defect-labelled filing (tracker MCP create, `gh issue create --label`) made before the run searched the tracker for an existing ticket (`bug-report` gains Step 0b: the ticket's sub-tasks and links, open and recently closed bugs with the same symptom; a defect that already has a ticket gets a comment there instead), or that cites no defect recorded as `bug`, and a sign-off while a `[SENTINEL <ticket>-D<n>]` or a defect-reporting verdict comment has no recorded confirmation; each refusal says to dispatch the reproducer. A hand-back that names defects without an adapter-recorded verdict opens with an "Unconfirmed defects" line naming them; defects confirmed in an earlier segment of a resumed run count, so a resume that dispatches no reproducer no longer raises a false alarm. Every `bug` verdict carries reproduction evidence, and a UI defect a reproduction video by default (`playwright-cli video-start`, a `video-chapter` per step, `video-stop`; schema fields `surface` and `video`); the adapter does not record a `bug` whose evidence is empty or missing on disk, or a `ui` bug without a non-empty video. The verdicts are consolidated in `docs/evidence/<ticket>/defect-audit.md`, a sixth deliverable; only `bug` gets a sentinel; R5 scores 0 for a reported defect without a verdict; `bug-report` refuses a ticket without one; reporting gains §9d on where each defect is filed and the tracker automation filing triggers. In the ticket run this comes from, 3 of 8 sentinels marked `@known-defect` were not bugs once reproduced independently: one intended, one a spec ambiguity, one never seen live.
- **A hand-back is held while the run's experts still work.** A harness may run an orchestrator's foreground dispatch in the background. The orchestrator's turn then ended with a status word while its expert worked, the adapter delivered that as the hand-back and dropped the run, and the expert's report had nowhere to go: three times in one ticket run. Now a status-word turn with experts still registered is held with a note to the orchestrator; when the last expert reports, the orchestrator is told so, and its next status-word turn is the hand-back. An expert whose turn ends with no status word and no report on disk is still at work (it waits on its own background run) and stays counted. A hand-back is held once, so an expert that never reports cannot hold a run forever. When the last expert of a held run reports, the held hand-back is delivered at once, naming the reports that came after it (the harness does not reliably wake an orchestrator whose turn ended), and a resume may take over a run left held with no expert at work. The orchestrator ends waiting turns without a status word (`agents/achilles-orchestrator.md`, `controller-contract.md`).
- **Evidence videos from a JSON storyboard: `npx achilles-video`** (`bin/evidence-video.mjs`, `schemas/evidence-video.schema.json`, `skills/evidence-capture/references/evidence-video.md`).
  - **What a storyboard holds:** an off-camera login (unrecorded context or storage state), captioned steps, network captures and downloads, an evidence page, and the expected and actual result.
  - **What the player records:** an opening card; each caption alone for 2.2 s, then its action at 600 ms; an evidence page with the decisive text highlighted and scrolled into view; and a closing caption. It writes `.webm` and H.264 `.mp4`.
  - **The manifest:** step start times, expectations, captures with headers stripped and `${env:…}` values masked, and a decode check of each file.
  - **Where it is used:** the reproducer records UI defects with it by default.
  - **Why:** it is built from the reproduction videos of a ticket run, which a developer could follow without context.
- **No AI signatures on anything outbound** (`skills/achilles-orchestrator/references/outbound-text.md`, `claude-code/hooks/attribution.ts`). The rule that kept AI attribution out of commits and PRs now covers every surface a run writes for someone else: issue and PR comments and reviews (`gh issue create|edit|comment`, `gh pr comment|review`), tracker tickets and comments, pages and chat messages sent through MCP tools, and report documents (`docs/**`, `tests/e2e/docs/*.md`, evidence `summary.md`, the deck and catalogue). One detector also catches the `Claude-Session:` trailer and the `🤖 Generated` footer. A message citing a file of the checkout a reader cannot open (the repository has no remote, the file is not committed, or its commit is on no remote branch) is refused too, with the fix: push and link, attach, or describe. A signature is refused; agent framing in an outbound message ("a separate QA agent", a brief pasted as a template, harness internals) gets a note. A ticket run had posted reproduction notes framed as agent output, and its local commits carried AI trailers added by the harness default.
- **Three test-quality rules for authors and the composition judge** (`agents/achilles-author.md`, `skills/review/SKILL.md`): a suspected app bug is never asserted as the expected result (keep the correct assertion, tag `@known-defect`, point at the finding); data a test uses up is restocked or reseeded, and a premise skip never covers data the suite depleted itself; waits are on conditions, `steps.pace` only for a deliberate rate limit. The BookHive onboarding on pi shipped four 5xx-as-expected assertions, 21 stock-dependent premise skips and ten fixed 1.5 s pauses, all approved.
- **Thinking effort per role.** `agents/achilles-{inspector,author,doc-writer}.md` set `effort: medium`; the orchestrator and the reviewer (the judge) set none and take the session's. Claude Code registers the agents with that effort; pi passes it as `--thinking`, and the parent's level to the roles without one.
- **Resume by run id.** `delegate_qa` takes an optional `run` and `/achilles` takes `resume <run-id> [notes]`, on Claude Code and on pi: the run keeps its id and `.achilles/runs/<id>/` directory and the orchestrator is told to read its `resume.json` first. Without it every delegation made a new run, and a resume depended on the task text. A run with no `resume.json`, a malformed id or one still running is refused. On pi, an orchestrator or expert process that cannot start now hands back `BLOCKED` instead of never answering.
- **Run progress.** The adapter tracks each run's stages (the phases of the pipeline ledger it writes, else a `plan` in its `resume.json`), the experts at work and the ones that handed back. The status line names the stage and the experts by brief, the pane draws a stage checklist, `.achilles/runs/<run-id>/progress.json` holds it all for the main session to read, and a stage that ends while stages remain queues a short progress prompt for the main session to relay.
- **`achilles-orchestrator` skill** with seven workflows (`author-scenario`, `onboard`, `map-journeys`, `expand-coverage`, `hunt-bugs`, `repair-suite`, `verify-change`): routing table with entry conditions, preflight (cascade level, resume files, tooling, questions), dispatch contract (briefs and reports as files, role → agent → skill table, concurrency, fresh reviewer), worker return contract, upward hand-back contract (`DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT`, `BLOCKED`), ten scope rules, one verification bar, state and commit discipline.

The adapter registers them from these files at session start; a bare `achilles-<role>` type is rewritten to the plugin-qualified one.

### Upgrading from 0.1.7 or a 0.2.0 branch install

The earlier installers copied the harness into `.claude/` (or `~/.claude/` for `-g`). 0.1.8 does not remove those copies, and the old hooks keep running until you do.

1. With the old package still installed, run `npx achilles-uninstall --project` (and `--global` if you installed with `-g` or had the user-level routing skill). 0.1.x had no uninstaller: continue with step 2.
2. By hand, in each `.claude/` directory Achilles wrote to (and `~/.claude/`): delete the 41 Achilles hook scripts under `hooks/` plus `hooks/factory/`, `hooks/lib/`, `hooks/data/` and `hooks/bin/jq`; the 25 copied skills under `skills/` (and `sql-client`); the 22 generated agents under `agents/`; `kernel-mandate.json`, `kernel-mandate.md`, `kernel-mandate.achilles.json`, `kernel-mandate.achilles-new.json`, `achilles-qa.kernel-mandate.json`; `achilles-install.json`; the routing skill `~/.claude/skills/achilles/` and `~/.claude/achilles-install.json`.
3. In `.claude/settings.json` (and `~/.claude/settings.json`), remove every `hooks` entry whose command points into `.claude/hooks/` or `~/.claude/hooks/`. Your own entries stay.
4. Install 0.1.8 (`npm i -D @civitas-cerebrum/achilles`, or the marketplace install) and restart Claude Code. Drop `ACHILLES_PROTOCOL`, `KERNEL_MANDATE`, `CIVITAS_SKIP_HOOK_INSTALL` and `CIVITAS_SKIP_JQ_INSTALL` from shells and CI; use `ACHILLES_SKIP_CLAUDE_REGISTRATION=1` where CI used `CIVITAS_SKIP_HOOK_INSTALL=1`.
5. Replace the old slash commands (`/onboarding`, `/coverage-expansion`, `/test-repair`, `/companion-mode`, …) with `/achilles <task>` or the `delegate_qa` tool. Projects with `achilles-factory-rules.json` keep it; the factory rules are read by the spec-hygiene hook and the CLIs.

## 0.2.0 — never published, superseded by 0.1.8

0.2.0 was never published to npm. Its kernel, activation, install-copying and uninstall items below are superseded by 0.1.8 and listed for anyone who installed it from a branch; the remaining items (CLIs, reporter behaviour, Bash parsing, mandate grants that became agent scopes) carried into 0.1.8 in their new form.

### Upgrading from 0.1.7 (superseded)

- **One-time overwrite.** 0.1.7 kept no install record. The first 0.2.0 install replaces every hook, hook library, hook data file and skill file in `.claude/` (for `-g`, in `~/.claude`) whose content differs from the package, including ones you edited. Postinstall prints how many files it replaced. From then on, a file you edit is never overwritten or pruned; postinstall warns once and leaves it.
- **Restart Claude Code** after the install to pick up the new hooks.
- **User-level copies.** A local install no longer copies skills and agents to `~/.claude`. - **Staged mandate.** If `.claude/kernel-mandate.json` differs from what Achilles staged, it is left as it is and the new QA mandate is written beside it as `kernel-mandate.achilles-new.json`, with one notice. An unedited copy is refreshed.
