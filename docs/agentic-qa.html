Agentic QA Get Started
Doctrine

Agentic Shift-Left

Every team adopting AI-assisted development hits the same wall. Agents write features in minutes. They also write brittle tests, hard-code selectors that break on the next PR, and skip quality gates nobody enforces. The suite bloats, the flake rate climbs, and trust collapses.
The traditional shift-left response shifts the work left without shifting the worker. Agentic shift-left shifts both.

Part I

The Agentic Shift-Left
Lifecycle

Four stages. A human starts it, agents do the heavy lifting, a human confirms the result, and agents guard it going forward.

01
Human

Triage

A human reads the ticket, the PR, or the feature brief and makes the CX/revenue call: does this change affect something a customer would notice? This is the one decision the methodology refuses to automate. An agent can assess technical risk, but the question "will a customer care?" requires business context that lives outside the codebase.

02
Autonomous

Automate

Sub-agents own the work. The methodology decomposes test automation into roles that can be independently dispatched, each with isolated context and a schema-validated return contract. Independent journeys are dispatched in parallel; each journey runs through composer → reviewer cycles until approved.

03
Human + Harness

Confirm

The tests get tested. Every test must be proven to fail where the fix is absent (negative control). Adversarial probes challenge the tests themselves. The harness blocks QA sign-off until evidence exists. Coverage is a human responsibility: the QA engineer owns what must be covered.

04
Autonomous

Guard / Heal

Gated releases, layered verification. Self-repair establishes a baseline by running the failing scope three times, then classifies each failure from its own evidence — trace, console, network: fails every run, it's a deterministic failure (an app bug, filed with evidence; the test is left alone); passes sometimes, it's a flake (quarantined with evidence); mechanical drift, it's healed autonomously. Each test ends green, quarantined or explained.

Guard Layers

Once tests are committed, the methodology prescribes a layered, gate-first test architecture:

Regression
Runs in the go-live pipeline. A regression failure stops the release — regression is a gate, not an alarm.
Smoke
Targets individual features, pages, and components. Runs on every pull request. Speed is their contract.
E2E
Verifies complete user journeys. Every step happens in the browser — replicating the user's experience as closely as possible.
Self-Repair
Autonomous triage — app bugs, test drift, and flakes classified from evidence. Mechanical repairs apply themselves; semantic changes, such as re-baselining an assertion, return as operator-pending for a person to decide.
Part II

The Architectural
Foundation

A test that hard-codes CSS selectors is a test that breaks when a class name changes. An agent that writes tests with hard-coded selectors produces a suite that rots faster than it grows.

Separation of Concerns

The foundation is a three-layer separation. When a frontend redesign changes every data-testid in the application, zero test files change. Each layer is the single source of truth for its concern.

Test Code
Owns: Business intent
Changes when a requirement changes
Steps API
Owns: Interaction mechanics
Changes when the framework evolves
Page Repository
Owns: Selectors
Changes when the UI is redesigned

Tests Anyone Can Read

The Steps API is the interface between human intent and automated verification. A product owner can read the test and know what it checks. An agent can write it without knowing how click-interception retry works under the hood.

await steps.on('addToCartButton', 'ProductPage').click()
await steps.on('cartCount', 'CartDrawer').verifyText('1')

The framework manages stability (auto-wait visibility, scrollIntoView, click-interception detection with classified retry), logging (zero log lines in project test code), and selectors (resolved at runtime from the page repository).

Part III

Commit or
Discard

Tests are discardable by default. The verification work is still required. But committing to the permanent suite is a separate decision with a separate gate.

The agent proposes durable automation only when CX/revenue impact justifies permanent regression coverage. A human confirms the proposal. Without explicit confirmation, the test stays in the evidence bundle and is not committed to the repository.

Commit

High CX / revenue impact

A login-flow change that affects every user → permanent regression test joins the suite, guarded by pipelines going forward.

Discard

Verified, low impact

A tooltip copy fix → verify it, attach the evidence, discard the test. The suite stays lean; the evidence bundle stays complete.

The commit-or-discard gate prevents suite bloat — most test suites grow without bound and eventually collapse under their own maintenance weight.

Part IV

Enforcement, Not
Instructions

The distinction between a methodology and a best-practices document is enforcement. The critical rules are backed by Claude Code hooks that deny the action when a precondition is not met. The hooks act while an Achilles skill is running, and the operator can switch parts of the enforcement off. The sections below list what runs, what each part denies, and how to turn it off.

48 hooks ship with the package. That count is the 41 top-level hook scripts plus 7 opt-in factory gates under hooks/factory/. 39 are enforcement gates, defined as scripts whose name ends in -gate.sh or -guard.sh; the rest record state or write summaries. 47 are registered in hooks/data/hook-manifest.json; the 48th, kernel-mandate-role-gate, is run by the kernel wrapper (see the role kernel below). Hooks register with Claude Code at npm postinstall: per project with a plain install, system-wide with npm install -g.

Hooks pass through unless the protocol is active in the session. Activation comes from ACHILLES_PROTOCOL=1, an Achilles skill call, a typed /<skill> or an Achilles-shaped dispatch. ACHILLES_PROTOCOL=0 stops a new session from activating; it does not deactivate a session that is already active. A few hooks have their own scope and run regardless (the four ledger gates, client-term-guard, deck-inspection-gate).

The role kernel

The role kernel gives each dispatched role its own grants: allowed tools, Bash command patterns, readable paths and writable paths. The package ships 23 roles in hooks/data/achilles-qa.kernel-mandate.json. Postinstall stages that file as .claude/kernel-mandate.json and never overwrites a project copy; an upgrade writes the new mandate beside it as kernel-mandate.achilles-new.json (KL-11). The kernel is vendored and maintained upstream. Decisions are logged to .claude/kernel-mandate.state/decision-log.jsonl.

When it binds. The registered hook is achilles-kernel-activation-gate, a wrapper that runs the kernel only while an Achilles skill is running. A project that only installed the package is not governed until a skill starts. If the kernel script is missing, the wrapper denies when the project has a kernel-mandate.json and allows otherwise.

How to switch it off. Set KERNEL_MANDATE=0 (or false or off) in the operator shell. This bypasses the kernel only; the Achilles gates above keep running. It exists because some work is refused under an active kernel: perf-onboarding, repair-worker-* dispatches and contribution handovers (KL-05, KL-07).

What it does not do. It does not read dispatch briefs (KL-01), it screens code that roles write rather than sandboxing it (KL-02), and the orchestrator may still write under tests/** (KL-13). Denials are pinned by hooks/tests/cases/85-qa-mandate-scopes.sh.

❯ [BLOCKED] Role 'orchestrator' may not write 'playwright.config.ts' — it is outside the role's write scope.
write scope: .achilles/**, .gitignore, docs/evidence/*/brief.md, tests/**, ...

What the Bash guards cover

protected-artifact-bash-guard, playwright-cli-isolation-guard and the factory state-gate and spend-gate judge the plain words of one command line. They cover common agent commands: plain writes, redirects, tee, sed -i, cp/mv/rm and the usual git restore forms. Obfuscated or exotic shell is out of scope (KL-15, KL-17, KL-20), and a script staged by an earlier call is not followed. ledger-integrity-chain detects an out-of-band ledger change after the fact.

Part V

The Honest
Constraint

A methodology must be honest about what it cannot yet do.

The lifecycle works within the boundaries of the environment it runs against. When that environment is production — when every test hits a live database, real payment processors, and actual customer-facing state — the methodology must exclude its most critical flows.

Checkout. Registration. Payment. Password reset. Account deletion. These are the flows with the highest CX/revenue impact, and they are the flows that cannot be safely automated against a production environment.

The methodology covers these flows architecturally. Exercising them requires a fully controllable test environment — a faithful replica of production without live connections to payment processors, identity providers, or customer-facing state — and full control over test data: the ability to programmatically generate, seed, and clear it so every run starts from a known baseline.

Platform Coverage

The second constraint is platform. The element layer is already platform-agnostic by design: Element is an interface, WebElement is its Playwright implementation, and PlatformElement is the Appium/WebDriverIO implementation beside it. The page repository resolves the same named selector through UiSelector on Android and predicate strings on iOS.

What is not here yet is the rest of the lifecycle. The agent skills, the harness gates, and the self-repair driver all assume a Playwright browser session today. Mobile support is on the roadmap, not in the package. Until it lands, treat everything on this page as a doctrine for web applications — the methodology generalises, the tooling does not yet.

What Achilles Is Not

It is not a hosted runner: suites run on your machine or your CI. It runs on Claude Code only. It does not cover native mobile. It does not heal tests at runtime: achilles-self-repair works offline on a red suite. No benchmark of detection or flake rates is published. The 20 known limits (KL-01 to KL-20) are in known-limits.md.

The Difference

Why Not Just Prompt
Better?

AI test generators produce tests. Achilles enforces a methodology around them.

Prompt-driven testing

Ask your copilot to write Playwright tests. You get tests — with hard-coded selectors, no negative control, no evidence bundle, and no gate preventing a flaky test from merging. The agent follows instructions. Nothing enforces them in the session.

Achilles

The agent writes tests through a three-layer architecture that isolates selectors from logic. Enforcement hooks deny ticket sign-off without an evidence bundle, and non-draft pull requests without an adversarial review receipt, while an Achilles skill runs. The methodology is the codebase, not a wiki page the agent never reads.

Adoption

Getting
Started

Achilles runs on Playwright. If your stack uses Playwright, integration is additive — you don't rewrite existing tests.

Install the two npm packages. The harness hooks register automatically via postinstall. Point the page repository at your application's selectors. Write new tests through the Steps API — existing Playwright tests continue to run unchanged alongside them.

Achilles runs on Claude Code only, version 0.2.0: postinstall registers the hooks and the role kernel as Claude Code hooks. The hook scripts are plain shell that read a tool call on stdin and return an allow or deny decision, but nothing else registers them, and the skills assume Claude Code tools.

After install, the 39 enforcement gates act in any session where an Achilles skill runs; they pass through otherwise. The 7 factory gates are separate and start only when you commit a rule file. Sign-off then requires an evidence bundle and an adversarial review receipt. To remove Achilles, run npx achilles-uninstall (--global, --project <dir> and --dry-run are accepted); it reverses what postinstall recorded in achilles-install.json. Other CLIs in the package: achilles-mutate, achilles-show, achilles-self-repair, achilles-scenario-lint, achilles-selector-evidence.

open source
